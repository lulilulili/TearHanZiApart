## 全部失败字的追踪

[`verification/harmony-sc-4f67abc-failures.json`](verification/harmony-sc-4f67abc-failures.json)
包含全部 **880** 个失败字的原始告警、相关笔序、楷体笔型、部件路径与
修复方向。`index` 是程序使用的零起点索引，`strokeNumber` 是人工查看的
第一笔、第二笔等一基笔序。文件带原始 JSONL 的 SHA-256，避免与旧版
`verifyOut/` 的不同基线混淆。

归类来自告警与结构数据，表示待验证的共同原因，不把同部件自动等同于
同一缺陷。基线的一些告警只记录前 8 个病笔或笔对，因此清单保证覆盖
全部失败**字**，不声称枚举每字的全部病笔。

较集中的字族：

- TYPE / 底横：最深部件为“一”的横有 115 个字，主要是口旁封底横。
- SPLIT / 門：竖对应 34 个字、横折钩对应 16 个字；两组可重叠。
- TYPE / 糹竖：24 个字。
- AREA / 艹竖：14 个字。
- AREA / 鸟：点 11 个字、横折钩 10 个字。

这些聚类指导优先级；修复采用几何条件，不按这份字符清单决定是否运行。

## 修复与验收原则

1. 保持 `verify.py` 的失败规则与阈值不变；生产修复不能靠改校验提高通过率。
2. 先复现最小字族，再比较原失败字与原通过字；保存源代码、规则、字体、
   数据的指纹，批次内部只用冻结的源文件与独立 B 缓存。
3. 每字都要有记录；重复、缺失、缺字状态改变与新增 ERROR/UNION 均阻止验收。
4. 原通过字变失败，以及原失败字出现新的失败类别，必须检查，不能用净改善
   掩盖回退。
5. 逐笔目检典型修复，不把整字并集一致当作笔画语义正确。
6. 原始 `retainRatio` 是重构环节保留弧长占比；布尔修改后的最终路径没有
   重新计算该值，因此只能作过程指标，不能当作逐笔最终精度。

## 验收结果

当前工作树已冻结三项几何修复：冗余孤片去重、输出退化路径回传救济流程、
以及按楷体参照轴的横/竖轴向守卫。验证证据如下：

- `python -m unittest discover -s .local -p "test_*.py"`：4/4 通过。
- `python -m compileall -q strokelab`：通过。
- 典型字 `永、汉、国、爱`：最终输出路径复算覆盖率均为 100.0%，溢出率均为
  0.0%。
- COUNT 高风险字 `婭、獅、蝴、龜`：当前实现均不再触发 COUNT；其中 `龜`
  仍有约 1% 的短/超面积软指标波动，需在后续 AREA 专项中复核。
- 门框样本 `門、閂、閉、開、閑`：当前实现不再触发 SPLIT；`閃` 仅剩
  TYPE，`閏` 剩 TYPE/AREA，说明门框碎片修复有效但会暴露原先被碎片掩盖的
  身份/面积问题。
- 通过字回归抽样 10 字：0 个新增硬性告警。失败字抽样 20 字中仍有 11 字
  告警，符合“修复失败字而非放宽校验”的预期。

上述结果不能替代 9,570 字的完整重验。原始全量基线仍为 8,690/9,570
（90.80%）；`_reverify_fail.jsonl` 是旧批次的部分结果，不能与当前工作树
直接合并。完整续跑应使用串行模式避免 Windows 多进程句柄限制：

```powershell
python -X utf8 reverify.py sc_fail_chars.txt _reverify_fail_current.jsonl 0 1646 1
python -X utf8 reverify.py sc_pass_sample.txt _reverify_pass_current.jsonl 0 800 1
```

当前剩余问题集中在 TYPE/AREA 的部件级归属（尤其“一、糹、口、隹、艹、鸟”）
以及复合笔画内部的语义段归属。AREA 现行统计按目标笔画面积总和归一化，遇到
合法重叠时会放大笔间耦合；下一轮应先改为按原字形总面积和楷体逐笔占比计算
期望值，再重新跑全量，且保持 `verify.py` 的失败阈值不变。
