# 项目代码风格规范(用户裁定)

## 命名

| 元素 | C++ / 新 JS | Python(既有仓库) |
|---|---|---|
| 函数/方法 | 大驼峰 `BuildLibrary()` | 保持仓库既有小驼峰 `buildLibrary()`(全量改名churn过大,迁 C++ 时统一转大驼峰) |
| 参数/局部变量 | 小驼峰 `strokeWidth` | 小驼峰(仓库既有约定) |
| 常量 | 全大写下划线 `MAX_STROKE_COUNT` | 同左 |
| 类 | 大驼峰 | 大驼峰 |

变量名必须有意义、可读;禁止 a/b/tmp1 式命名(循环下标 i/j/k 除外)。

## 函数与行

- 函数入参 ≤5 个;超过时用结构体/类/dataclass 封装。
- 单行 ≤120 字符。
- 单函数有意义行(不含注释/空行)尽量 ≤50 行(Python 可放宽,但要努力)。
- C++ 函数调用/声明超 120 字符换行时,续行与函数左括号对齐,或与上一参数
  对齐(Google style)。

## 函数组织

- **不要在函数内定义函数**(闭包),除非是传给逐帧驱动/排序的一次性
  小回调。共享状态经结构体/ctx 显式传递,帮助函数放模块级(可单测、
  可复用、C++ 迁移零障碍)。历史包袱:pipeline 巨函数时代闭包是唯一
  选择,PipelineCtx 落地后该理由已消失;包内为保 parity 按原文搬移的
  残留嵌套函数,后续以 parity 硬门为界逐步提级为模块级。

## 封装与注释

- 多做有意义的类封装;数据在流程间传递用明确协议(结构体/dataclass),
  不用裸 tuple/dict 串场。
- 注释:功能说明简短;**涉及算法的必须详细**(为什么这样做、阈值来历、
  踩过的坑)。本仓库传统:算法注释里记录教训字例(如"爱5竖曾被…"),延续。

## 架构约束(重构裁定)

1. 两大模块:**汉字拆解**(strokelab 管线)与**矢量动画**(viewer 特效库),
   互不依赖内部实现,只通过拆解结果 JSON 协议通信。
2. 拆解模块按流程切子模块(对齐/D构建→指派→仲裁→精调→切割→重构→收口),
   各流程入参出参协议明确(PipelineCtx 结构),改一段不伤整体。
3. 动画库按效果拆文件;单元操作(采样/插值/缓动/适配)入参出参统一,
   放共享 utils 复用。
4. 通用算法(重采样/插值/对齐/包围盒)一律进 utils,禁止复制粘贴副本。

## 性能与安全

- 结构设计时就考虑性能:热路径避免重复解析/重复构造(memo/缓存),
  批量化优先(numpy 先例:逐点循环→矩阵 2.5×)。
- 不引入安全问题:不 eval 外部输入、路径拼接防穿越、服务端参数校验。
- 未来 C++ 迁移:稳定内核用 pybind11/Rust 下沉,Python 留胶水层——
  子模块边界=未来 FFI 边界,设计时保持数据协议可序列化。
